# Firebase を使うときの設計(費用と攻撃への備え)

「他の人生」・ログイン・コメント・ハートを動かすときの、設計の方針。まだ実装していない(Firebase 未設定)。
作業は dev ブランチで行い、main への統合・本番反映は、必ずユーザーの確認を取る。

## 方針

1. **無料プラン(Spark)のまま始める**。無料枠を使い切ると、自動で止まる(請求は出ない)。有料プラン(Blaze)は、アクセスが本当に増えてから検討する。Blaze の予算設定は「通知」だけで、自動停止ではない。入れるときは、自動停止の仕組みを先に作る。
2. **一覧の読み取りを、Firebase から外す**。「他の人生」の一覧は、定期的に JSON ファイルにして、Cloudflare に置く。読む人は、そのファイルを見る(読み取りゼロ・配信無料)。Firebase は、投稿(書き込み)と、ログインと、ハートの書き込みにだけ使う。
3. **App Check を入れる**。正規のサイトからのアクセスだけを受け付ける。
4. **Firestore ルールで、1回の読み取りを制限する**。一覧の取得は、10件まで。
5. **投稿の制限**。投稿は、ログインした本人だけ。1日に数件まで。お問い合わせフォームには、Cloudflare Turnstile(無料)を付ける。

## 読み取りの見積もり(目安)

- 一覧は 1ページ10件。1ページ=10回の読み取り。詳細を開くと、1件につき1回。
- 「他の人生」を開いた人は、平均 約17回(1.6ページ + 詳細1.5件)。
- 無料枠は、読み取り 1日5万回 → 開く人が 約2,900人/日 まで、0円。サイト全体の訪問者に直すと 約1万〜1万4,000人/日(開く人が2〜3割のとき)。
- 1日1万人が来て、その2割5分が3ページ見る場合: 月 約80円。全員が3ページ見る最悪の場合: 月 約720円(Blaze のとき。単価は 10万回あたり 約0.06ドル、1ドル=150円で計算)。
- 一覧を JSON で配ると、一覧の読み取りは、ゼロになる。

## 保存容量

- 無料枠は 1GiB。公開用の人生は、1件 10〜30KB と見て、約5万件で埋まる。超えても、1GiBあたり 月 約30円。
- ルールの上限は、1件 100KB(`firestore.rules` の `request.resource.size() < 100000`)。

## ハート(他人の人生への)

- 押せるのは、ログインした人だけ。1人が、1つの人生に1回。もう一度押すと、取り消す。
- 保存: `shared/{人生のID}/hearts/{ユーザーID}`(中身は、押した日時だけ。個人情報は保存しない)。
- 件数: 人生のドキュメントに、件数の欄(`heartCount`)を持つ。ハートの追加・削除のたびに、1つ増減する(トランザクション。件数を数えるための、追加の読み取りが、いらない)。
- ルール: 作成・削除は、自分の記録だけ。読み取りは、だれでも。
- サンプルの人生には付けない。自分の人生にも押せるが、ランキングには入れない。
- 並び替え: 新しい順 / ハートが多い順(上位100件を、JSON にして配る)。
- 件数の水増し(複数アカウント)は、完全には防げない。件数は目安として扱う。

## コメント(人生への)

- ログインした人だけが投稿できる。1日に数件まで。文字数は、500字まで。
- 保存: `shared/{人生のID}/comments/{コメントID}`(投稿者のID・本文・日時)。
- 通報と削除: 投稿者本人は、削除できる。運営は、コンソールから削除する。
- 迷惑投稿の対策: Turnstile、文字数・回数の制限、通報のボタン。
- 表示は、詳細ページを開いたときに、新しい順で10件ずつ読む。

## ページネーション

- カーソル方式(最後に見た記録の次から、10件)。ページ番号のジャンプは、しない。
- 同じ一覧を開き直したときの読み取りは、端末の中に、数分間保存して、減らす。

## 実装の順番

1. Firebase のプロジェクトを作る(ユーザーが、Google アカウントで操作する)。Spark プランのまま。
2. 環境変数 `NEXT_PUBLIC_FIREBASE_*` を、Cloudflare Pages に設定する。
3. `firestore.rules` を、本ファイルの方針に合わせて更新し、デプロイする。
4. App Check と、Turnstile を設定する。
5. 一覧の JSON 配信(定期的に作り直す仕組み)を作る。
6. ハート → コメントの順に、実装する。
7. dev で動作を確認してから、本番へ(反映は、毎回ユーザーの確認を取る)。
